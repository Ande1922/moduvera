# V0.1 Vertical Slice

## Outcome

Deliver the first runnable multi-process microservice slice on the way to the [complete non-deployment scaffold](./NON-DEPLOYMENT-SCAFFOLD.md). This slice is an implementation milestone, not the final deployment design.

The slice is complete when:

1. a tenant-authorized caller creates an Order;
2. Order obtains the product and price through the Catalog service interface;
3. Order persists as `PENDING_STOCK` and records `ReserveInventoryCommand` in the same local transaction;
4. Inventory consumes the command idempotently and records either `InventoryReserved` or `InventoryRejected`;
5. Order consumes that result idempotently and changes state;
6. the same independent pytest black-box scenario starts with only public HTTP calls and observes the final result through public HTTP;
7. `./mvnw verify` uses JDK 26, Maven 3.9.16, and Spring Boot 4.1.1; the V0.1 reference path uses PostgreSQL, MyBatis-Plus, Spring Cloud Stream, and the Kafka Binder. The external deployment mechanism remains open.

## Historical first implementation step

Bootstrap the build and composition shell:

- root Maven reactor and dependency-management module;
- Maven Wrapper 3.9.16;
- JDK 26 compiler and Enforcer baseline;
- one executable `app-monolith` module containing only composition and startup;
- one context-load smoke test proving the selected Spring Boot/JDK baseline.

This step deliberately did not create empty Catalog, Order, or Inventory module shells. Later work added each module together with real behavior and verification. This section is implementation history; current evidence is maintained only in [the product surface](./SCAFFOLD-PRODUCT-SURFACE.md).

## Deep-module seams

- Catalog exposes one interface that returns the authoritative product/price snapshot needed for ordering.
- Order exposes one command interface for creation and one query interface for observing status; persistence and Outbox mechanics stay behind those interfaces.
- Inventory exposes command handling through its owned asynchronous command contract; stock mutation and deduplication remain inside the module.
- `app-monolith` is not the Golden Path, but ADR 0022 makes it a required second topology with focused acceptance. Deleting it must not delete business behavior, and completing it must not duplicate the full infrastructure matrix.
- Tests cross the same interfaces as callers. Internal implementation seams are not promoted into shared `common` or `port` packages.

## Completed evidence cadence

- Step 1 — completed: JDK 26 + Maven Wrapper + Spring context smoke test.
- Step 2 — completed: pure Catalog/Order/Inventory behavior and unit tests.
- Step 3 — completed: `TransactionBoundary`, Data Starter, guarded migration, service schemas and durable transaction/message integration.
- Step 4 — completed: separate App Assemblies, real HTTP/JWT/Kafka paths and independent public pytest black-box acceptance.
- Step 5 — completed for the retained V0.1 scope: focused MySQL Repository/migration/messaging compatibility TCK. ADR 0022 adds the modular-monolith topology as subsequent required work; jOOQ and additional brokers remain deferred.

## Start gate

The Maven `groupId` and Java base package are fixed as `io.github.ande1922.moduvera`. PostgreSQL/MyBatis-Plus and Spring Cloud Stream/Kafka are the confirmed V0.1 runtime choices. The local acceptance harness does not settle production deployment or exact CI cadence.
